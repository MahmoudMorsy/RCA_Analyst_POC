# RCA Analyst POC v0.7.1 — Release Notes

## Release type

**Corrective patch release.** v0.7.1 keeps the v0.7.0 architecture and frozen semantic rules unchanged. It fixes implementation-contract defects exposed by the first live TC12 run.

## Why v0.7.1 exists

TC12 failed on v0.7.0 after the architecture split, but not for the reason TC12 had failed in older releases. Both 27B Phase-A chunks completed normally and remained far below the 16,000-token large-case ceiling. The failure instead exposed several integration gaps between the new focused stages:

1. the 4B source-availability model understood the source states correctly but returned compact strings where the schema required structured `IntakeField` objects;
2. the Atomic Claims model returned a valid JSON array while the shared structured parser accepted only a top-level object;
3. the requirement-language normalizer mixed applicability, trigger and required-behavior semantics;
4. Phase A duplicated decomposition and could omit trigger/persistence fields that had already been captured structurally;
5. dependent validator errors created noisy repair cascades;
6. a deterministic repair `NO_CHANGE` could terminate the repair loop instead of escalating.

The failed session preserved the canonical case, model attempts and last validated semantic object, making these defects diagnosable rather than losing forensic state.

## Corrected architecture contracts

### Source Availability

Natural-language interpretation remains a Qwen3.5-4B responsibility. Python does not learn phrases such as `Not available` or multilingual equivalents. v0.7.1 only normalizes the model's compact envelope after the LLM has already classified the source as PRESENT/ABSENT/UNKNOWN/NOT_MENTIONED.

### Atomic Claims

The prompt now demands a top-level object containing `claims`. The structured parser also supports a bounded mechanical fallback: a bare list is accepted only when the requested schema has exactly one array property. No claim text or meaning is rewritten during this recovery.

### Requirement Language Normalization

The 4B contract is stricter:

- applicability groups contain only IF/scope preconditions;
- pure WHEN/UPON requirements keep event semantics out of applicability DNF;
- `becomes` maps to `trigger_event=BECOMES`;
- required behavior is represented separately from applicability;
- `shall remain CLOSED` is a positive equality obligation, not an inverted predicate;
- process concepts are not invented when the source wording does not define a machine-readable signal/state equivalent.

### Phase-A bridge

Python may project already-normalized structured fields into missing Phase-A decomposition slots:

- event trigger text from normalized trigger signal/event/value;
- timing text from numeric `timing_limit_ms`;
- persistence interval text from normalized persistence semantics;
- required behavior only when the normalized contract supplies it and Phase A omitted it.

This is execution of an LLM-normalized contract, not Python natural-language interpretation.

### Validator and repair sequencing

- APPLICABILITY-labelled needs are mechanically kept out of evaluation evidence.
- Required response-signal names can be taken from the normalized requirement contract even if no observation of that response exists yet.
- Trigger-timestamp needs are deferred until trigger decomposition exists.
- A deterministic `NO_CHANGE` escalates the same repair target to 27B semantic arbitration when fallback is enabled; it no longer terminates the whole repair loop.

## TC12 token-budget conclusion

No additional token increase was made. The v0.7.0 live TC12 Phase-A calls ended normally at approximately 3,936 and 2,684 completion tokens respectively. Therefore the existing **16,000-token** large-case budget is retained for TC12/TC21-class cases.

## Expected TC12 behavior after the patch

The important expected compliance state remains:

- REQ-1201: APPLICABLE / NOT EVALUABLE
- REQ-1202: NOT APPLICABLE / NO COMPLIANCE VERDICT
- REQ-1203: APPLICABILITY UNKNOWN / NOT EVALUABLE
- REQ-1204: APPLICABLE / VIOLATED, deterministic **1100 ms vs 800 ms**
- REQ-1205: APPLICABILITY UNKNOWN / NOT EVALUABLE
- REQ-1206: NOT APPLICABLE / NO COMPLIANCE VERDICT
- REQ-1207: APPLICABLE / SATISFIED
- REQ-1208: APPLICABILITY UNKNOWN / NOT EVALUABLE
- REQ-1209: APPLICABILITY UNKNOWN / NOT EVALUABLE
- REQ-1210: APPLICABILITY UNKNOWN / NOT EVALUABLE

TC12 remains a live acceptance gate. v0.7.1 should not be frozen until that local run succeeds.

## Live Pipeline expectations

The existing 18-stage architecture is unchanged. For TC12, the important observability expectations are:

- Source Availability completes with the LLM classification rather than dropping to schema fallback.
- Content Classification runs normally.
- Atomic Claims completes without an array-envelope failure.
- Requirement Language Normalization produces cleaned structured hints.
- Phase A runs as two relationship-preserving chunks under the 16k large-case budget.
- Python Requirement Validation derives the 1100/800 ms REQ-1204 violation.
- Requirement Repair should be skipped or narrowly targeted; a deterministic NO_CHANGE must escalate rather than abort the loop.
- Phase B sees read-only authoritative compliance facts.

## Compatibility

- No architecture topology change from v0.7.0.
- Existing v0.6.x/v0.7.0 session fields remain load-compatible.
- No frozen state/transition/interval semantics were weakened.
- No Python multilingual absence-sentinel list was introduced.
- Large-case defaults remain threshold 8, target chunk size 6, max completion 16,000.

The packaged source is expected to pass **151 automated tests** before release. The final package must also pass compile, fresh-extraction test, ZIP-integrity and cache-cleanliness checks.
