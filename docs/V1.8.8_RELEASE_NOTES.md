# RCA Analyst v1.8.8 Release Notes

**Application:** v1.8.8  
**Embedded RCA Core:** v0.8.7 candidate  
**Basis:** clean v1.8.7 release plus the complete RunPod 17-case session `RCA_20260902_151632_21c9e1` and the preceding live TC17 sessions.

## Why v1.8.8 exists

v1.8.7 solved the dominant provider-integration problem exposed by the first 27B TC17 experiments: explicit Thinking Off now reaches llama.cpp/Qwen and semantic-call output sizes/runtime dropped sharply. That made it practical to run the complete 17-case live regression bundle without changing the architecture.

The full suite then exposed systemic semantic-contract defects that were not visible from TC17 alone. All 17 cases completed transport/runtime execution, but only 2/17 met the existing semantic-acceptance manifest. The important failure classes were:

- compiler batches could omit whole Requirement IRs;
- source-clause audit inventories were frequently absent or incomplete;
- signal/value required behavior, triggers, timing and persistence could remain transport-valid but non-executable;
- independent verification could share a normative-polarity mistake with the compiler;
- narrative evidence could become compliance-material too easily;
- exact-source grounding was too brittle around bullets, line breaks and deliberate ellipsis excerpts;
- semantic arbitration was invoked for every case, largely to repair schema/provenance omissions instead of genuine semantic disputes;
- RCA synthesis could cite a verified semantic fact ID that the final hypothesis gate did not recognize;
- semantic acceptance could pass a conservative expected verdict even when internal semantic-integrity ERRORs caused that verdict;
- the Web Tests selector exposed only completed cases, so the currently running case became unreachable after browsing an earlier result, and single runs had no testcase item.

v1.8.8 addresses those failure classes as systemic contracts. It does not hardcode any testcase outcome, add Python natural-language interpretation, weaken evidence semantics, or transfer compliance authority away from Python.

## RCA Core v0.8.7 changes

### 1. Bounded missing-Requirement recovery

Every Requirement Compilation batch now carries an explicit expected ID set. Python validates:

```text
requested requirement IDs == returned Requirement IR IDs
```

If one or more IDs are missing, Python performs exactly one bounded semantic recompilation for the missing IDs only. Recovered IRs are merged back in the authoritative source order. Unknown extra IRs are not promoted into the authoritative batch.

If an expected ID remains missing after the bounded recovery, it stays a material semantic-integrity failure. Python does not synthesize a Requirement IR from prose.

This directly addresses the live TC20 pattern where REQ-2002 through REQ-2005 disappeared from compiler output.

### 2. Source-clause audit becomes a first-class structural completion target

`RequirementStructuralPatchBatch` can now repair a complete `source_clauses` inventory when Python identifies missing provenance. The completion contract requires a complete replacement audit inventory for that requirement rather than a few detached fragments.

Structural completion can now target:

- required behavior;
- trigger;
- timing;
- persistence;
- complete source-clause audit inventory.

The path is bounded to at most two compact completion passes. Pass 1 repairs executable shells/provenance. A second pass is allowed only when the first repair reveals a wholly missing top-level field, for example a timing object represented by a newly restored TIMING source clause.

The repair model still interprets source language. Python only identifies which structured fields are incomplete and merges validated patches.

### 3. Stronger Requirement IR provenance/executability integrity

Python now checks semantic-ID/source-clause linkage for executable condition predicates, trigger, required behavior, timing and persistence. A transport-valid object with missing executable fields or missing provenance is not allowed into deterministic compliance.

The compiler prompt explicitly requires:

- one grounded source-clause audit entry for every material semantic element;
- non-empty executable signal/operator/value for signal-state obligations;
- trigger signal/event semantics when the source defines an event;
- timing/persistence semantic IDs and source linkage;
- no empty `source_clauses=[]` for an executable requirement.

### 4. Independent normative-polarity reconstruction

The semantic verifier now reconstructs normative polarity independently from the source rather than inheriting the compiler label. The contract explicitly distinguishes:

- positive `shall` / `must` obligations → `MANDATORY`;
- `shall not` / `must not` / equivalent prohibitions → `PROHIBITIVE`;
- permission forms → permissive semantics where supported.

This is an LLM semantic contract, not a Python phrase-list rule. Python still compares structured verifier output against compiled IR and escalates material mismatches.

### 5. Safer exact-source grounding

Source grounding remains strict against invented content, but no longer fails solely because formatting changed. Python grounding normalization now tolerates source-preserving differences such as:

- bullet markers;
- line breaks;
- harmless punctuation layout.

Explicit `...` or Unicode ellipsis may represent omitted source text only when the retained segments occur in source order. Invented words remain unsupported.

This addresses live diagnostic/historical snippets where a model quoted exact source content across bullet/line boundaries while preserving the false-positive protection demonstrated by TC16-style hallucinated spans.

### 6. Evidence materiality requires an authoritative structured dependency

Unresolved narrative ticket/report/history facts no longer become compliance-material merely because they mention the same signal or carry a loose requirement association.

Compliance-material evidence ambiguity requires an authoritative structured path, such as:

- a direct observation explicitly linked to the requirement;
- explicit current-ticket scope metadata;
- a material evidence role recognized by the semantic contract.

This preserves the frozen rule that same-signal overlap alone is not sufficient materiality. Direct evidence that can genuinely alter applicability/compliance remains conservative when unresolved.

### 7. Compact issue-scoped semantic arbitration

Semantic arbitration remains limited to one material primary-model call. Its exact authoritative source packet is now built deterministically from the material issues:

- only implicated requirement source text;
- only implicated evidence source text/structural fields;
- relevant ticket context/user instructions.

This reduces prompt growth and truncation risk while retaining exact source authority. The arbitration validator remains strict: a replacement IR or fact must be executable and source-grounded; notes-only repair is not accepted.

The intended effect is also architectural: routine provenance/executability defects should be resolved in bounded semantic preparation rather than making arbitration a normal mandatory stage.

### 8. Verified semantic fact IDs are valid RCA provenance

RCA synthesis may ground a hypothesis in a verified semantic fact rather than only its parent canonical evidence item. The final RCA consistency gate now accepts:

- canonical evidence IDs; and
- semantic fact IDs whose annotation resolution is `VERIFIED`.

Unknown or unresolved fact IDs remain invalid. This fixes the live TC21 identifier-namespace mismatch without weakening hypothesis evidence validation.

### 9. Semantic-acceptance integrity gate

The regression acceptance evaluator now adds an always-on check that final validated semantic-integrity `ERROR` count is zero. A testcase can no longer pass merely because a compiler failure happened to produce the expected conservative `UNKNOWN / NOT EVALUABLE` verdict.

This closes the false-clean acceptance pattern observed in TC4/TC11.

## Web / backend changes

### Running testcase lifecycle is authoritative

The Run Manager now registers a testcase lifecycle record before pipeline execution:

```text
RUNNING → PASS / FAILED / CANCELLED
```

The same record is updated in place rather than appending a testcase only after completion. Lifecycle state is persisted separately and included in `/runs/{run_id}/result` during execution.

### Universal Tests selector

The Tests selector is now available for both single and batch runs.

- the currently running testcase appears immediately;
- a user can inspect a finished testcase and switch back to the live running testcase;
- a single run has one testcase item instead of hiding the selector;
- live Pipeline, Logs and partial Stats remain available for a running case;
- result-only views state that the final result is not yet available until completion.

The browser remains presentation-only and does not infer RCA state.

## Regression coverage

v1.8.8 adds regressions for:

- bullet/line-break/explicit-ellipsis grounding while rejecting invented spans;
- non-material narrative evidence despite signal/requirement overlap;
- complete source-clause structural patch replacement;
- missing Requirement IR bounded recovery and authoritative ordering;
- compiler/verifier provenance and normative-polarity prompt contracts;
- verified semantic-fact RCA provenance;
- internal semantic ERRORs forcing semantic-acceptance FAIL;
- single-run RUNNING testcase lifecycle visibility;
- batch RUNNING testcase lifecycle visibility.

All prior frozen evidence/state/transition/timing regressions remain part of the suite.

## Release validation

The final release is gated by:

- complete automated pytest suite;
- Python compile check;
- Web JavaScript syntax check;
- FastAPI `/health`, `/config`, `/capabilities` smoke tests;
- clean ZIP integrity/content audit;
- full test-suite replay from a fresh extraction of the exact final ZIP.

Automated tests verify software contracts. They do not prove live-model semantic acceptance.
