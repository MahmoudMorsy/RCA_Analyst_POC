# RCA Analyst POC v0.7.0 — Release Notes

## Release type

**Minor architecture release.** v0.7.0 changes the reasoning topology while preserving the frozen evidence semantics and Python final-authority rules validated in the v0.5.x/v0.6.x line.

Starting with v0.7.0, every release must include a dedicated file named `docs/V<version>_RELEASE_NOTES.md` in addition to the cumulative `VERSION_HISTORY.md` and newest-first `CHANGELOG.md`.

## Why v0.7.0 exists

The v0.6.5 overnight realistic regression exposed a pattern: the system's compliance truth was generally strong, but large monolithic language/reasoning calls were doing too many jobs at once.

- **TC12** exhausted primary structured-output space on a distractor-heavy case because hidden reasoning consumed most of the output budget before the JSON could finish. TC21 is the same class of stress case.
- **TC17** showed that a single broad 4B intake call could inconsistently interpret `Not available.` as diagnostic content instead of source absence.
- **TC8** showed that a compound reported sentence (`PREPARED` timely, `ACTIVE` late) must be decomposed before deterministic evidence-conflict comparison.
- **TC13** showed that hypothesis wording could overstate correlation as causality.
- **TC16/TC17-style hypotheses** could merely restate a compliance failure instead of proposing a mechanism.
- **TC4** showed that response evidence can be mapped from a point where the applicability condition is explicitly false unless requirement language is normalized into executable structured predicates.

The architectural answer is decomposition by responsibility, not a growing collection of Python natural-language heuristics.

## New authority model

### Qwen3.5-4B — small language-normalization tasks

The fast model is split into focused stages:

1. **Source Availability** — classify requirements, historical tickets, diagnostics/BZD and trace as `PRESENT`, `ABSENT`, `UNKNOWN`, or `NOT_MENTIONED`.
2. **Content Classification** — extract source-backed content after availability is known; bare headings/metadata are not engineering evidence.
3. **Atomic Claim Extraction** — split natural-language statements into independent claims, including timing and causal-strength annotations. Raw deterministic trace assignments are excluded.
4. **Requirement Language Normalization** — produce non-authoritative structured predicates, nested applicability logic, trigger/response fields, timing limits, persistence and explicit relationship IDs.
5. **Hypothesis Epistemic Review** — classify generated hypotheses as mechanism candidates, compliance restatements, root-cause claims, evidence summaries, etc., and propose `KEEP`, `REWRITE`, or `DROP` actions.
6. **Final Wording Review** — retain the v0.6.4/v0.6.5 relevance/sufficiency/verdict consistency contract.

The 4B does not own evidence IDs, transition inference, timing arithmetic, requirement verdicts or final compliance truth.

### Qwen3.8-27B — two deep reasoning phases

**Phase A — Requirement Reasoning**

- faithful requirement meaning;
- normative type;
- applicability semantics;
- evidence role/relevance/sufficiency;
- inherited/explicit requirement scope;
- requirement decomposition.

Phase A is explicitly prohibited from emitting RCA hypotheses, historical synthesis or diagnostic mechanism conclusions.

**Python authoritative compliance checkpoint** runs immediately after Phase A and establishes immutable requirement results and timing facts.

**Phase B — RCA Synthesis**

- current engineering picture;
- historical precedent comparison;
- diagnostic interpretation;
- evidence-backed candidate mechanisms;
- case-validity gaps and next evidence.

Phase B receives the validated compliance state as read-only facts and cannot modify requirement objects.

Existing primary-model repair is retained as conditional semantic arbitration when a genuine Phase-A semantic error remains after deterministic/fast repair routing.

## Large-case handling

Large Phase-A inputs are now routed structurally:

- default large-case threshold: **8 requirements**;
- default Phase-A chunk target: **6 requirements**;
- explicitly related requirement IDs stay in the same connected component/chunk even if this exceeds the nominal chunk target;
- default large-case primary completion budget: **16,000 tokens**;
- normal cases retain the standard primary budget;
- `finish_reason=length` is explicitly recorded as output-token exhaustion, and the one bounded retry becomes output-oriented with reduced reasoning effort.

This is intended to address TC12/TC21 without changing the validated model settings for normal cases.

## Python responsibilities retained and extended

Python remains authoritative for:

- source-span/provenance enforcement;
- canonical evidence IDs/classes;
- timestamp and clock handling;
- `STATE_SAMPLE`, `TRANSITION`, and `INTERVAL_STATE` mechanics;
- observation-group/same-clock correlation;
- deterministic timing arithmetic;
- frozen applicability/evaluation asymmetries;
- structured predicate execution after the 4B has normalized requirement language;
- repair allowlists and revalidation;
- final compliance gate and deterministic report formatting.

### TC4 contextual evaluation mapping

Python can now execute the 4B-normalized applicability predicate against a correlated point. If the applicability condition is definitively false at that point, response evidence from that same point is removed from the evaluation bucket. Python does not parse the original requirement sentence to do this.

### TC8 proposition-level conflicts

Reported/direct timing conflict comparison uses source-backed atomic claims when available. A sentence containing multiple propositions is no longer treated as one indivisible pass/fail assertion.

## Cancellation hardening

If cooperative cancellation closes an active streaming response and the underlying HTTP reader subsequently raises a transport/`NoneType.read`-style exception, the client now translates that path to `AnalysisCancelled` when the cancellation token is set. A user stop should therefore be represented as `CANCELLED`, not as a semantic testcase failure.

## Live Pipeline v0.7.0

The GUI now exposes the new architecture explicitly:

1. User Input
2. Input Classification
3. 4B Source Availability
4. 4B Content Classification
5. Python Canonicalization
6. 4B Atomic Claims
7. 4B Requirement Language Normalization
8. 27B Phase A — Requirement Reasoning
   - dynamic child stages for each Phase-A chunk
9. Python Requirement Validation
10. Requirement Repair / 27B Arbitration
11. Authoritative Compliance State
12. 27B Phase B — RCA Synthesis
13. RCA Validation / Repair
14. 4B Hypothesis Epistemic Review
15. 4B Final Wording Review
16. Python Final Gate
17. Deterministic Report Formatter
18. Final Output

Every actual model call remains recorded in session `attempts`/`stats`, while the new intermediate structured objects are exported separately.

## Session/API compatibility

v0.7.0 adds optional session fields for the decomposed stages while retaining the existing v0.6.x fields. Existing saved sessions and test adapters are not deliberately invalidated.

New optional session fields include:

- `source_availability_normalization`
- `content_classification`
- `atomic_claim_extraction`
- `requirement_language_normalization`
- `rca_synthesis`
- `hypothesis_epistemic_review`
- `raw_requirement_reasoning_json`
- `raw_rca_synthesis_json`

## Default configuration additions

- `primary_large_case_max_tokens = 16000`
- `primary_large_case_requirement_threshold = 8`
- `primary_phase_a_chunk_size = 6`
- `fast_source_availability_max_tokens = 900`
- `fast_content_classification_max_tokens = 2800`
- `fast_atomic_claim_enabled = true`
- `fast_atomic_claim_max_tokens = 1800`
- `fast_requirement_language_enabled = true`
- `fast_requirement_language_max_tokens = 2400`
- `fast_hypothesis_review_enabled = true`
- `fast_hypothesis_review_max_tokens = 1200`

The existing fast-repair and final-review non-thinking defaults remain intact.

## Regression protection

v0.7.0 adds tests for:

- decomposed architecture defaults;
- source-availability structural enforcement without Python phrase interpretation;
- TC4 false-applicability-context evaluation mapping;
- TC8 atomic-claim conflict handling;
- relationship-preserving Phase-A chunking;
- immutable Phase-B requirement truth;
- hypothesis `DROP`/`REWRITE` epistemic actions;
- v0.7.0 Live Pipeline stage visibility;
- 16k large-case Phase-A routing;
- release-history/release-note continuity.

The previous TC1–TC5 and v0.6.x regression protections remain in the automated suite even when a testcase is removed from an expensive overnight bundle.
