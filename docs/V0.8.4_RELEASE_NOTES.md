# RCA Analyst POC v0.8.4 — Release Notes

## Release purpose

**Live-TC17 semantic-transport isolation and scope hardening.** v0.8.4 keeps the v0.8 semantic-compiler / deterministic-compliance architecture and fixes failure modes exposed by the TC17 v0.8.2 live run.

The live failure showed that the 4B model could understand the mixed German/English nested requirement correctly while still emitting malformed structured output. Two independent transport problems were present:

1. malformed Requirement IR Boolean shape (for example duplicate/overwritten `children` arrays and one-child `AND`/`OR` nodes);
2. malformed evidence-annotation envelopes where `facts` were nested under `resolution` and an annotation-level `scope_id` was emitted.

The first class was already addressed by v0.8.3's transport-valid-vs-executable Requirement IR split. v0.8.4 completes the same principle for evidence and removes the combined small-case semantic-preparation call that allowed an evidence-schema defect to discard otherwise useful Requirement IR output.

## Main changes

### 1. Requirement compilation and evidence annotation are always separate

The production semantic stage no longer uses one combined response model for small cases.

Normal structured-case topology is now:

```text
4B Requirement Semantic Compilation
        ↓
optional targeted 4B Requirement Structural Completion
        ↓
4B Evidence Semantic Annotation
        ↓
optional targeted 4B Evidence Semantic Completion
        ↓
4B independent Requirement-vs-IR Verification
```

Larger requirement sets still use bounded RequirementCompilationBatch calls. Requirement count only affects 4B output sizing; it never creates additional 27B calls.

This isolates failures: a malformed evidence object cannot invalidate a correctly compiled Requirement IR batch, and a malformed Requirement IR does not require evidence reannotation.

### 2. Evidence transport canonicalization

`EvidenceSemanticAnnotation` now tolerates a narrow class of model schema-envelope mistakes without performing language interpretation.

If the model explicitly returns:

```json
{
  "evidence_id": "EVID-X",
  "resolution": {
    "facts": [...],
    "unresolved_semantics": []
  },
  "scope_id": ""
}
```

Python may structurally lift the already-explicit `facts` and `unresolved_semantics` into the correct annotation envelope. It does not derive signal names, values, temporal meaning, scope referents, or requirement links from prose.

A non-empty stray annotation-level `scope_id` is **not** assigned to a fact. It is preserved as unresolved transport information so it cannot silently become executable coverage.

### 3. Component-specific evidence repair

After transport normalization, structured evidence defects receive at most one targeted fast-model reannotation before 27B arbitration.

Examples include:

- a material persistent fact marked `scope.resolution=RESOLVED` but missing `scope.scope_id`;
- another material evidence object that remains structurally non-executable.

Only the affected evidence IDs are reannotated. Requirement compilation is not repeated.

### 4. Natural-language persistence requires a concrete scope ID

A language-derived `PERSISTENT_STATE` becomes executable `INTERVAL_STATE` evidence only when all of the following hold:

```text
fact.resolution == VERIFIED
fact.temporal_semantics == PERSISTENT_STATE
fact.scope.resolution == RESOLVED
fact.scope.scope_id is non-empty
```

`RESOLVED + ""` is not accepted as interval evidence.

The evidence prompt instructs the model to use a concrete semantic scope identifier such as `CASE_EVALUATED_INTERVAL` only when the supplied context actually resolves that interval. Otherwise it must return PARTIAL/UNRESOLVED.

### 5. Arbitration evidence repairs are strict replacements

The existing v0.8.2 strict arbitration rule is extended to evidence.

An evidence annotation returned by the 27B arbitrator must be fully VERIFIED. A persistent-state repair must include a concrete resolved `scope_id`. If scope/meaning remains ambiguous, the arbitrator must leave the blocking issue in `unresolved_issue_ids` instead of returning a pseudo-repair.

### 6. Specialized 4B prompts

Production now uses separate system prompts for:

- Requirement Semantic Compilation;
- Evidence Semantic Annotation;
- Requirement Semantic Verification.

This reduces heterogeneous-schema pressure on the 4B and explicitly forbids the TC17 envelope/Boolean-shape failures.

## Architecture boundaries unchanged

v0.8.4 does **not** move natural-language interpretation into Python.

- LLMs interpret requirement/evidence language.
- Python validates structured contracts and executes verified semantics.
- Python does not infer a missing signal or scope from prose.
- One 27B case-level semantic arbitration call remains the maximum normal compliance escalation.
- Deep RCA remains conditional on actual mechanism-oriented evidence.
- Original source text remains immutable provenance but is not automatically re-sent to downstream RCA.

## Regression additions

v0.8.4 adds regressions for:

- TC17-style evidence annotation with `facts` nested under `resolution`;
- ignoring an empty stray annotation-level `scope_id` without losing explicit fact semantics;
- refusing to assign a non-empty annotation-level scope to any fact in Python;
- blocking persistent natural-language evidence with `RESOLVED` scope but empty `scope_id`;
- strict 27B rejection of persistent evidence pseudo-repairs without scope ID;
- always-separated requirement/evidence calls even for TC17-sized cases;
- targeted evidence completion without repeating Requirement IR compilation;
- preservation of the existing TC12/TC17 deterministic verdict expectations.

## Live validation status

This release is an implementation candidate. It should not be frozen as a validated semantic baseline until live TC12 and TC17 runs complete with the expected deterministic outcomes and acceptable model-call behavior.
